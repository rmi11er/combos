# Behavioral RFQ blacklist sniffer

This is the implemented, narrower first step following `RFQ_FORWARD_FLOW_ARCHITECTURE.md`: passive collection and offline screening of creator behavior. It needs no model prices or private fills. No trading code or live blacklist integration is included.

`scripts/rfq_sniffer.py` records Kalshi communications and public trades, then updates a persistent SQLite evidence database. Creator IDs with repeated qualifying bursts are exported to `blacklist.json`. The database accumulates evidence across captures; the export is rebuilt from that durable state. Continue recording blocked IDs so their subsequent behavior remains visible.

## Run

### Installed nightly schedule

The macOS user LaunchAgent `local.combos.rfq-sniffer-nightly` checks once per minute and starts one 3,600-second capture at approximately **18:00 America/Chicago** daily, followed by analysis and evidence validation. Daylight saving is handled explicitly by Python's timezone database, independent of the Mac's local timezone. The first scheduled evening after installation is September 8, 2026. The saved September 7 data covers only approximately 19:20–20:48 Central; it cannot establish the daily peak. 18:00–19:00 is the initial sampling window, not a measured maximum.

The Mac must be logged in and awake during the 18:00–18:04 start window. Missed windows are skipped; waking later does not start an off-window capture. Once started, `caffeinate` prevents idle sleep through capture and analysis. Closing the lid, shutting down, or logging out can still interrupt it. A lock and a date-specific run directory prevent overlapping or duplicate daily attempts; failed attempts are recorded and not automatically restarted that evening.

The dispatcher is `scripts/rfq_sniffer_nightly.py`, with its shell runner and source LaunchAgent plist in `scripts/scheduling/`. Credentials are sourced from the existing `~/.codex/.env` at execution time and are not copied into the plist or reports. Each run uses the existing v2 evidence database and policy, refreshes `output/rfq_sniffer`, validates the evidence, and snapshots the five result files under `runs/rfq_sniffer_nightly/YYYY-MM-DD/report/`. Check that day's `status.json` and `run.log`, or `runs/rfq_sniffer_nightly/latest_status.json`, for success/failure. `policy_comparison.json` is a historical September 7 comparison and is not regenerated by nightly runs.

Raw captures and evidence are retained; the September 7 hour used about 1.1 GB compressed raw storage plus database growth. New captures are skipped with a recorded failure if less than 10 GiB is free. No historical evidence is automatically deleted. Analysis/validation continues after 19:00 and takes longer as the database grows.

To disable the installed job:

```sh
launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/local.combos.rfq-sniffer-nightly.plist
```

To re-enable it:

```sh
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/local.combos.rfq-sniffer-nightly.plist
```

Use the existing `KALSHI_API_KEY_ID` and `KALSHI_PRIVATE_KEY_PATH` environment variables. With those credentials available:

```sh
.venv/bin/python scripts/rfq_sniffer.py run --seconds 600
```

Defaults: journal directories under `runs/rfq_sniffer`, evidence at `data/derived/rfq_sniffer/evidence_v2.sqlite`, and exports at `output/rfq_sniffer`. This runs for ten minutes, processes the capture, updates the exports, and exits. Longer bounded runs can use `--seconds`, up to one day. Use an always-on host for long captures. The database lock prevents concurrent scans/exports against the same evidence database.

Capture and analysis can also run separately:

```sh
.venv/bin/python scripts/rfq_sniffer.py capture --out runs/rfq_sniffer/capture_example --seconds 600
.venv/bin/python scripts/rfq_sniffer.py scan runs/rfq_sniffer/capture_example --db data/derived/rfq_sniffer/evidence_v2.sqlite --out output/rfq_sniffer
.venv/bin/python scripts/rfq_sniffer.py export --db data/derived/rfq_sniffer/evidence_v2.sqlite --out output/rfq_sniffer
```

The capture directory must be new. Re-scanning a completed journal is idempotent. Requests are additionally deduplicated by RFQ ID. Interrupted scans commit batches and can be rerun; partially written/unclosed raw journals need recovery before scanning. Ctrl-C closes the current capture journal; run `scan` afterwards to analyze it. Keep journals chronological. Late previously unseen requests are retained but explicitly excluded from burst escalation.

Optional `--policy config/rfq_sniffer.json` pins nondefault thresholds. Optional repeated `--mappings <runtime-config.json>` loads exact ticker-to-fixture keys; otherwise the detector uses same-event overlap and an explicitly labeled NFL/MLB/NCAAF/NBA/WNBA/NHL event-suffix heuristic. Version 1 evidence remains in `evidence.sqlite`; the revised defaults use `evidence_v2.sqlite`. Mapping and policy changes require a separate evidence database, so results cannot silently mix definitions.

## What causes a flag

A creator receives a burst flag when any of these default conditions holds within 60 seconds:

| Reason | Default condition |
|---|---|
| `high_request_rate_watch` | At least 120 distinct RFQs; watch only, never counts toward a block |
| `high_request_rate` | At least 600 distinct RFQs; eligible to count toward a block |
| `identical_parlay_spam` | At least 30 identical selected-leg sets, regardless of other templates in the creator's window |
| `minor_edit_parlay_spam` | At least 30 requests in one similar template, with variation present; no creator-wide dominance requirement |
| `large_concentrated_parlay_spam` | At least 10 similar requests with 12+ legs and at least 60% of legs in groups of 3+ sharing a fixture/event, without requiring that template to dominate the creator's window |

Near matches require at least six unique legs, an edit allowance of `min(5, max(2, ceil(0.05 * smaller_leg_count)))` replacements/additions/removals measured by the larger one-sided set difference, and at least 80% overlap with a fixed anchor. Side and scalar-settlement differences remain part of each leg key. Matches do not chain through gradually changing anchors. Only the 64 most recently active template anchors per creator are retained, so very diverse flows can be undercounted by similarity; the general rate rule still applies.

Three **block-eligible** windows, separated by at least 60 seconds and all within 24 hours, add a creator to the provisional blacklist for 24 hours. The 120/minute watch events have a separate window clock and cannot suppress a later 600/minute flag or contribute to blocking.

A creator gains `recurrent` confidence when at least two distinct capture journals each have at least three block-eligible windows within the evidence lookback, and new qualifying evidence is at least 30 minutes after the other period first qualified. Replaying the same journal or reconnecting does not create a new period. One long capture alone stays provisional. Recurrent entries expire after seven days, renewed by qualifying behavior; their supporting period references are retained. New creators may be blocked provisionally while accumulating recurrence evidence. One large parlay alone does not blacklist its creator. New evidence from widely separated days does not accumulate forever toward the burst threshold. The defaults are heuristic screening settings, not evidence of malicious intent or statistical correlation estimates.

## Later-trade context

For each RFQ, the report checks for a public trade on the exact same market at both 60 seconds and five minutes after local RFQ receipt, requiring the trade's event timestamp also to fall within that interval. An old delayed print is not counted as later activity.

- `later_public_trade_same_market`: a later print was observed. It may belong to anyone.
- `no_public_trade_observed_in_covered_window`: both subscriptions were acknowledged and the horizon falls inside a continuous observed coverage interval, with no matching later print.
- `censored_or_trade_coverage_unknown`: the capture ended too early, a disconnect/sequence discontinuity or receive gap intervened, or the subscriptions were not established.

No later public trade is useful triage context, **not proof that the RFQ did not fill**. Missing activity never triggers a blacklist on its own. Short-lived markets, public feed delays, off-book visibility and RFQ-to-trade attribution are not inferred. Five-second receive gaps conservatively interrupt coverage. The final 60 seconds and five minutes respectively commonly have censored windows. The extended horizon is supporting triage context and never independently promotes a creator to the blacklist.

## Outputs

- `blacklist.json`: `creator_ids` is the active ignore list. `entries` contains IDs, status, first/last qualification, expiry, provisional/recurrent confidence, qualifying capture periods, reason codes, evidence IDs, and both public-trade horizons. Expired historical entries remain visible but are omitted from `creator_ids`.
- `creators.csv`: ranked review of flagged creators, including request counts, maximum legs, concentrated requests, total and block-eligible burst counts, confidence, and both later-trade horizons. Start here for manual review.
- `evidence.jsonl`: each burst's exact counts, trigger RFQ, structural features, sample RFQ IDs and raw-journal row reference.
- `watchlist.jsonl`: all creators with any burst evidence, including those also blacklisted; consult `blacklist.json` for active status.
- `summary.json`: captured request/identity counts, flags, active blacklist size, coverage diagnostics and policy version.

Outputs replace their prior versions atomically per file after each scan/export. They are offline review artifacts; the files are not a cross-file transactional snapshot or a live execution policy service. Expiry is evaluated at export time. A future trading consumer must honor `expires_at` or refresh the export regularly, rather than treating an old `creator_ids` array as permanent.

The `extended_trade_context` fields and CSV columns ending in `_extended` use the configured five-minute horizon. `trade_context` retains the 60-second comparison.

The evidence database holds canonical leg sets and compressed references, while the raw journals retain original messages. Keep the journals that support a blacklist entry. No automatic retention or cloud upload is performed. The implementation favors a simple auditable batch job over a production low-latency service.
