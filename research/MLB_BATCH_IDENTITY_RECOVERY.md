# MLB batch identity failure: auditable recovery design

The safest recovery is a **new versioned execution root and source snapshot**, importing already certified work by hash and adding explicit unsupported-identity coverage. Do not change the old batch's frozen script, refresh its freeze hashes, erase its failed stage, or relabel unsupported All-Star fixtures as ordinary club games. Collection scope remains all 31 dates; pricing coverage can be narrower only with explicit exclusions and denominators.

This is a read-only design review. No jobs, source edits, manifest changes, provider requests or August outcome inspection were performed.

## Concrete failure and why a restart alone cannot fix it

`dated_fee_primary/batch_status.json` records July 11 cohort exit 0 with seven output hashes, followed by exchange attempt 1 exit 1. The log stops at `mlb_exchange_acquire.py:226`, calling `identity(ticker)` while building request windows; `identity()` raises `unresolved_fixture_or_doubleheader_identity`. Its team parser enumerates `TEAM_NAMES`, so an unsupported AL/NL identity fails before provider discovery/history work. The separate payoff audit owns the exact All-Star evidence and affected print count.

The exception is outside the later `pm_match` exception handler. Merely adding `unmatched` handling there cannot recover this failure. Moreover, `mlb_model_replay.py:risk_buckets` calls the same identity parser; skipping acquisition windows alone can still cause the replay to fail. A generic catch-and-continue would conceal the reason and could drop only one leg, creating a different bet.

The batch intentionally treats this as a nontransient failure and stops. Re-running unchanged inputs repeats the error; increasing retry counts spends time without addressing identity. The frozen closure includes acquisition, replay, batch, downstream scripts and core source modules. Existing batch restarts require identical configuration and verify every frozen source plus completed stage hashes.

## Minimal safe source changes in a new version only

1. Add a deterministic, offline identity preflight before external acquisition. Cache each unique native leg's outcome: `supported_ordinary_fixture`, `unsupported_fixture_type`, or `ambiguous_or_malformed_identity`. Only the specifically reviewed unsupported category is nonfatal. Missing metadata, malformed timestamps, ambiguous ordinary clubs/doubleheaders, corrupted files and unexpected programming errors remain failures. Preserve the existing exact ordinary-game matching and payoff checks.
2. Record rejected **whole combos**, keyed by trade ID, with every problematic leg, reason, native evidence references and identity-policy version. Never remove a leg and price the remainder. Preflight must not use realized outcomes to decide eligibility. Native universe files and all rows remain unchanged.
3. Build acquisition windows for supported legs/combos with explicit statistics: all structural candidates, supported candidates, excluded unique prints, excluded quantities/premiums, unique legs/fixtures, jobs generated and mapping statuses. Distinguish identity support from source mapping/availability. Keep the original fee and price-time guards.
4. Apply the same versioned identity policy in replay **before** `SourceFairs.fair` and `risk_buckets`, with a dedicated scope/coverage reason. Unsupported combos remain in the native seller benchmark and unpriced coverage denominator. Supported-model outcomes and ordinary-game code paths must match baseline at zero policy effect.
5. Treat a date consisting entirely of unsupported fixtures as `complete_census_unpriced_identity`, not `complete_empty_eligible_scope`. The latter currently represents structurally empty input, and downstream code may turn it into an empty day. Retain explicit unpriced status in final coverage; do not create fabricated zero-trade performance or certify all required models as available.

For July 11, which also contains ordinary MLB markets, supported work should continue after preflight. A batch-level per-date blocker can let other dates progress while keeping an unresolved date visibly incomplete. This requires a bounded new-version state-machine change, not marking the old failed exchange complete. Validation must still require all 31 dates accounted for, with unsupported pricing gaps distinguished from pending tapes.

## Concrete migration sequence

1. Save an immutable recovery receipt containing the old batch manifest/status/log hashes, the July 11 cohort's seven certificates, the acquisition plan hash, old/new code hashes and the exact recovery policy. Verify the old batch PID/session is stopped. Leave public tape collectors independent and retain their current budgets/rate limits.
2. Prepare a new source snapshot and batch root, for example `dated_fee_identity_v2`, preserving the existing 31-date plan, fee scenarios, interpreter and cohort boundaries. Apply changes only in this new snapshot or separately named versioned scripts. The snapshot's `ROOT` must resolve to its own complete local dependency closure; running a clone that imports modified files from the old repository would defeat the freeze.
3. Import complete days as **certified references**, not newly claimed executions. A migration manifest records original stage commands, timestamps and output hashes; verify every old complete artifact before import. Avoid duplicating multi-gigabyte data. Existing `discover()` checks both lexical and resolved paths, so a new-root date symlink to an immutable old completed date can resolve to the original replay certificate. Never run a mutable stage through a whole-day symlink.
4. For July 11, create a real new date directory with only a read-only reference to its certified old `cohort`; exchange and all later output directories must be new and writable. Import only the completed cohort stage with its original evidence. Do not import the failed exchange as complete. Record the failed attempt separately as provenance; it need not consume the new implementation's retry budget.
5. For remaining dates, use real new date directories and the same original acquisition root. Reference validated existing raw caches only when their query identity and content hashes match. Do not overwrite old caches or assume a ticker filename alone establishes query equivalence.
6. Generate a new batch manifest from the new code/config closure. A small explicit import/migration routine must populate only certificates it has revalidated; do not hand-edit statuses to bypass execution. Fresh stage commands should identify new outputs, while imported stages retain their original origin. Confirm resuming an imported stage verifies content without rerunning or overwriting it.
7. Start the root-owned new batch only after offline tests and the migration receipt pass. First run July 11's preflight in plan-only mode, review the unsupported coverage and provider job delta, then proceed with the already authorized collection budget. Preserve failed receipts and atomic output completion markers.

This is more auditable than editing `TEAM_NAMES` to make AL/NL parse. Identity resolution would not establish ordinary-game payoff equivalence, and merely resolving their names could accidentally introduce an All-Star game into the strategy.

## Watcher and final-index implications

`mlb_spread_followthrough.py` and `mlb_completion_followthrough.py` accept a single `--batch-root`; their saved identity binds that path and code hashes. They cannot be silently repointed in place. Their `discover()` helper consumes only certified `complete` days, requiring a replay-stage hash, and rejects conflicting outputs for the same date. New source hashes or root paths require new watcher output directories. The old watchers may remain readable historical checkpoints; root should stop idle old-root watchers once their work is preserved, rather than expecting them to discover the new root.

Recommended compatibility approach: use the new root as a composite certified view of imported old days plus newly processed days, so existing single-root watcher semantics remain understandable. Create new follow-through manifests; import their already completed evidence by an explicit migration receipt or run only missing follow-through work. Do not copy an old watcher manifest and change its path field. `mlb_completion_followthrough` also derives cohort paths from each date, so the composite view must preserve `cohort`, `exchange`, `replay` and pricing-context access, not just opportunities.json.

Final longitudinal ingestion must use exactly one authoritative replay per date. Existing discovery supports multiple batch roots but rejects differing certified hashes for the same date. If a completed date is reprocessed under v2, it must receive a separately labeled experiment/cohort version; do not mix both copies in one final study. The full 48-policy scope and continuous risk/cash semantics remain unchanged. New unpriced-identity statuses must appear in final coverage and must not be counted as fully available model days.

## Offline acceptance gates

- Synthetic AL/NL or explicitly unsupported identity mixed with ordinary legs: entire combo quarantined, ordinary-only candidates retained; no outcome needed.
- Unsupported leg appearing in repeated combos: unique trade counts reconcile without double counting; no orphan leg pricing or risk key.
- Unknown/ambiguous ordinary fixture or doubleheader: remains a hard error; no fuzzy team/time relaxation.
- Supported-only saved day: exact request windows/jobs, mapping decisions, source availability, risk buckets, fee calculations and decoded replay results match the old version; path/provenance fields are the only allowed explicit differences.
- Empty supported subset: no invalid Gamma bounds, no provider requests, explicit complete-census/unpriced identity result; downstream coverage remains incomplete for models.
- Migration corruption, wrong hashes or conflicting same-date replays: fail closed. Imported files unchanged before/after; fresh stages never write through old-directory references.
- Restart/crash: atomic state and output certification, process cleanup, no completed-stage rerun and no reset of shared provider budgets.

## Open decisions for root

The separate payoff audit must decide whether All-Star coverage is merely unsupported in this research version or requires its own model/rules review. Neither decision reduces collection scope. A compatibility root with certified imports plus a narrow new preflight/replay policy is the smallest robust recovery; a wholesale old-manifest rewrite or broad exception swallowing is not warranted.

Source inspection: `scripts/mlb_historical_batch.py` (`stage_commands`, `run_stage`, `verify_frozen`, resume loop); `scripts/mlb_exchange_acquire.py` (`identity`, window preflight, `pm_match`); `scripts/mlb_model_replay.py` (scope loop, `risk_buckets`); `scripts/mlb_longitudinal_sweep.py:discover`; both follow-through watcher scripts. Failure evidence: `dated_fee_primary/logs/2026-07-11_exchange.attempt1.log` and current batch status. No implementation or job launch is implied by this document.

## Root preference: explicit same-path generation migration

After this review, root prefers preserving the existing output paths so watchers and downstream source references do not need a composite root. **This is acceptable as an explicit, audited generation change**, and is the lower operational-complexity option if the following gates are met. It supersedes the new-root preference above, not its requirements for preserved evidence, no silent refreeze and exact unsupported coverage.

1. Stop/reap the failed batch and any process that can execute the changed dependency closure. Keep unrelated raw-tape collectors running. Pause idle follow-through watchers before migration, even if their direct frozen list omits acquisition: imported `PairHistory`/identity functions can remain in process memory. A new file hash does not replace already imported Python objects.
2. Archive the original `batch_manifest.json`, `batch_status.json`, full code snapshot and July 11 failure log byte-for-byte in an immutable generation directory. Record their SHA256 values, current completed stage certificates, all 31 planned dates and exact source changes in a migration receipt. Keep the archived generation interpretable independently.
3. Apply only reviewed identity-policy changes after those processes stop. Generate a new manifest with an explicit generation ID, parent-manifest hash, receipt hash and changed-closure hashes. Do not simply replace the old freeze values without lineage. If the existing batch script cannot carry generation metadata, add a separately versioned migration/bootstrap wrapper rather than falsifying the original execution record.
4. Preserve every complete stage's status, original command/times and output hashes. Revalidate them all. Preserve the failed July 11 exchange attempt in the archived state and migration receipt; the next attempt must identify its new generation. Do not overwrite its failure log, declare success manually or rerun the already certified cohort. Existing attempt-count semantics can remain; document the implementation change before the next attempt.
5. Reconcile and restart watchers against the new generation. Their identities should include the **transitive** changed code closure, not only today’s short explicit lists. Retain completed replay hashes and prior follow-through outputs; unchanged inputs need not be recomputed. If watcher identity fields change, archive the old manifest and link the new generation explicitly. Fresh watcher output roots are also acceptable while keeping the batch root fixed.
6. Prove supported-only replay parity on saved data before restarting paid/public acquisition work. Then prepare July 11's request plan and exclusions. The separate identity audit reports only **4 of 28,473 eligible July 11 prints** affected by AL/NL; preserve all candidates and price supported legs, with those whole combos explicitly unpriced until identity/payoff support is reviewed. Do not add AL/NL name aliases that imply ordinary-game pricing approval.
7. Resume the full 31-date batch under the new generation. Final reports must disclose the version boundary and unsupported-print coverage. Existing frozen completed replays retain their original pricing version, while newly processed dates record the new version; supported-only parity justifies comparing them without claiming identical source hashes.

Same paths alone are not a problem. Silent replacement of their provenance is the problem. With archived generations and preserved stage certificates, this approach avoids redundant data copies and watcher path churn while keeping the failure and recovery fully reviewable.
